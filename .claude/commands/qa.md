name: qa
description: 複数リポジトリのPRを横断してQAチェックリストを作成する（各repo配下CLAUDE.md必須）
args:
  - name: targets
    description: "repo名:PR番号 repo名:PR番号 ... [NotionURL]"
    required: true

# 実行手順

## 0. 前提確認
- claude 配下で運用する
- 共通前提は claude 配下の CLAUDE.mdにある
- repo固有前提は 各 repo 配下の CLAUDE.mdにある
- /qa は「対象repo配下のCLAUDE.md読み取り」を必須とする

---

## 1. 引数解析
- repo名:PR番号 の形式を1つ以上含むこと（必須）
- httpから始まる引数は Notion URL とみなす（任意）

---

## 2. リポジトリ存在チェック（必須）

対象ごとに確認する：

(1) claude/{repo名} が存在すること  
存在しない場合は以下を出力して停止する：

「repo名 が claude 配下に存在しません。確認してください。」

(2) claude/{repo名}/.git が存在すること  
存在しない場合は以下を出力して停止する：

「repo名 は Git リポジトリではありません（.git が見つかりません）。確認してください。」

---

## 3. CLAUDE.md 読み取り（必須）

(0) 共通の CLAUDE.md を読む  
- claude/CLAUDE.md があれば読む  
- なければ claude/claude.md を読む  
- どちらもなければ以下を出力して停止する：

「claude 配下に CLAUDE.mdが見つかりません。共通前提ファイルを作成してください。」

(1) 各repoの CLAUDE.md を必ず読む  
- claude/{repo名}/CLAUDE.md があれば読む  
- なければ claude/{repo名}/CLAUDE.md を読む  
- どちらもなければ以下を出力して停止する：

「repo名 配下に CLAUDE.mdが見つかりません。repo固有前提ファイルを作成してください。」

(2) 優先順位  
- repo配下の CLAUDE.md の内容を優先し、共通 CLAUDE.md は補助として扱う

---

## 4. PR情報取得

claude/{repo名} に移動して以下を実行する：

gh pr view {PR番号} --json title,body,baseRefName,headRefName,files  
gh pr diff {PR番号}

PRが存在しない場合や取得に失敗した場合は：

「repo名 の PR {番号} を取得できませんでした。番号を確認してください。」

と出力して停止する。

---

## 5. 巨大PR対策（重要）

diff が非常に大きい場合：

- 変更ファイル一覧を優先して整理する
- ロジック変更箇所のみ要約する
- 追加行数・削除行数が極端に多いファイルを重点分析する
- 全文をそのまま展開しない

以下のように整理する：

- 変更ファイル数
- 主な変更カテゴリ（API/DB/ロジック/テスト/設定など）
- 影響が大きいファイルTOP3
- 仕様変更を伴う箇所

---

## 6. 変更内容の整理（まだQAは作らない）

各リポジトリごとに以下をまとめる：

- PRの目的
- 主な変更点
- 影響範囲
- repo固有前提（repo配下CLAUDE.md）に照らした注意点
- リスクになりそうな箇所
- 横断的な影響（API・DB・イベントなど）

その上で、全repoを総合して横断サマリを作る：

- 変更の全体像（何を達成する変更か）
- repo間の依存関係と影響伝播
- 一番事故りやすい統合ポイント（TOP3）

巨大PRの場合は詳細よりも構造理解を優先する。

---

## 7. 開発要件の取得と理解（Notion URL 指定時は必須）

- Notion URL が指定されている場合、そのページに記載された開発要件を必ず取得すること。
- MCP の「claude.ai Notion」コネクタを使用して本文を取得すること。
- 本文を取得したら、要件を構造化（目的・スコープ・非機能・制約）すること。
- 要件を理解しない限り、QAチェックリスト生成に進んではならない。
- 取得できなかった場合はその理由を明記し、要件の要点貼り付けを依頼する。

---

## 8. ここで必ず停止する

以下の文言をそのまま出力し、ユーザー入力を待つこと：

追加情報や捕捉事項があれば入力してください  
（なければ何も入力せずEnter）

ユーザーの入力を受け取る。

---

## 9. QAチェックリスト生成

追加情報および開発要件（Notion URL指定時はその内容も含む）を反映し、**リポジトリ単位を最優先**としてQAチェックリストを作成する。

### 出力方針

- リポジトリごとにセクションを分けて出力する。
- 各リポジトリ内で以下の観点に整理する。

  - A. 横断E2E確認（repo間の連携・契約・整合性）
  - B. リポジトリ別確認（repo固有前提に基づく）
  - C. リスク観点確認（事故りやすい統合ポイント中心）
  - D. ロールバック確認（戻し方・影響範囲・データ整合）

- 見出しには必ず引数で指定された実際のrepo名を使用すること。
- repo名は固定文字列にせず、動的に出力すること。

---

### チェックリスト形式

すべてのQA項目はチェックボックス形式で出力する。

形式は以下に統一する。

- [ ] テスト項目の内容  
  （優先度: 高/中/低 / 環境: xxx / 観点: xxx / 期待: xxx）

---

### 優先度

- 優先度は P0/P1/P2 ではなく「高 / 中 / 低」で出力する。
- 判断基準は以下とする。

  - 高：本番障害や重大なデータ不整合につながる可能性がある
  - 中：主要機能に影響するが致命的ではない
  - 低：軽微な表示・挙動・利便性への影響

---

### リグレッションテスト

- リグレッションテストの場合は、項目の冒頭に【リグレ】を付ける。

例：

- [ ] 【リグレ】既存フローが正常に完了すること  
  （優先度: 高 / 環境: staging / 観点: 既存ユーザ操作一連 / 期待: 変更前と同等の動作）

---

### ネストに関する注意

- ネストは深くしすぎないこと。
- 原則として1項目1チェックとする。
- Notionへ貼り付けても崩れない構造を優先する。

---

### 巨大PRの場合

diffが大規模な場合は以下を優先する。

- 代表的な変更カテゴリごとに整理する。
- 変更ファイル量よりも「事故リスクが高い箇所」を優先する。
- 網羅性よりも重大リスクの検出を重視する。

---

### 要件との整合性

- Notion等の開発要件がある場合は、必ず要件に対する充足確認観点を含める。
- 要件に明記されている非機能（性能・セキュリティ・制約など）もQAに反映する。
- 要件に記載があるがPR差分に反映されていない事項があれば、確認項目として追加する。
